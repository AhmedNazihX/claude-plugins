## Context
After this ships: no page mad-eye visits can reach it through a file, also after the fence lifts. We'd know because a curfew test denies mad-eye a `Read` under `.playwright-mcp/` with no fence set, and mad-eye's `tools:` lists `Read` as its only file tool.

Why this story: the commit security review of iteration 20 (S-064). The Playwright server saves every page it visits as `.playwright-mcp/page-*.yml` (spike S-L5, finding 4). While fenced, curfew denies mad-eye every read tool; once mad-eye navigates back and the fence lifts, the old file of the off-origin page is still there and readable. mad-eye never needs those files: `browser_snapshot` returns the page in its reply.

Design: mad-eye keeps `Read` only. Its `tools:` drops `Grep` and `Glob`, and curfew denies mad-eye `Grep`, `Glob` and `LS` always (the lists stay exact, decision 010). Curfew denies mad-eye a `Read` whose `file_path`, resolved with `os.path.realpath`, has a path part named `.playwright-mcp`. One path check is simpler and safer than keeping a search across the repo out of that folder. Other agents keep today's read rules.

Known limits, left as they are (review of the iteration 20 fixes): a preview page that leaves the origin later, on a timer, is not fenced until mad-eye's next response with a `### Page` section (a screenshot or console call before that passes); and whether a navigate-back response can carry the off-origin page's late console messages is unverified (the live run showed none). Both need the story's own app to misbehave on purpose.
