## Context
After this ships: a build stops for the user only for a real decision, and every finding, block and break leaves a reason. We'd know because over the next two iterations no story blocks with "Should it be fixed and built again?" or on a one-off accio hiccup; each `.accio/iterations/<N>.md` has one line per finding and block saying how it ended; every boggart break that reached a fix round came with a repro that failed twice on head; owl reports a cost for every build; and the guard and allow-list tests pass.

Why this story: S-053 turned off proxies, but CI run 39479645320 (commit f9c8bcd) still failed `accio-tests (macos-latest)` the same way: every test whose preview is `python3 -m http.server <port> --bind 127.0.0.1` gets "did not answer within 20s", and S-053/3's log tail came back empty. Tests whose server is a raw socket (`s.bind(...); s.listen(5)`) pass. Likely cause: `http.server.HTTPServer.server_bind` binds the port, then calls `socket.getfqdn(host)`, a reverse DNS lookup, and only listens after it returns. On GitHub's macOS runners that lookup can be slow, so the port refuses connections past the 20s limit. The log is empty because the server's "Serving HTTP" line goes to stdout, which Python buffers when it writes to a file, and no request ever reached it to log on stderr.

The fix is in the test only (a real preview is the user's own app): replace `self.serve` with a small server that serves the worktree's files without the `getfqdn` call (for example `http.server.SimpleHTTPRequestHandler` on a `socketserver.TCPServer`, or `HTTPServer` with `server_bind` reduced to `TCPServer.server_bind`), run with `python3 -u` so its first line reaches the log at once. If CI is still red, the log tail S-053/3 adds will now show whether the server got that far.
## Reuse
`self.serve` and `configure` in `accio/tests/test_preview.py`; the raw-socket `listen` server in the same file, which already passes on macOS CI.
