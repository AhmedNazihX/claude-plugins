## Context
After this ships: the user can use accio as their everyday coding workflow and finds it adds value, and we'd know because they use it themselves and learn from what goes wrong. For howler: after owl pushes, without being asked, a short report appears in the chat within a few minutes of CI ending. It gives PASSED or FAILED for each workflow and job; for a failure, the failing step or test and its error, `real` or `first failure`, and whether the cause lies inside the pushed range. We'd know by running one real iteration in this repo (howler itself), pushing, and seeing the report arrive while the user does something else.

This story is the by-hand spike S-029/0 from the design's Open questions. It needs the howler agent (S-002) to exist and must be done before S-003, the owl change. If step 1 fails, no option meets R4 and the design goes back to the user; S-003 must not start.

## Review notes
Run by hand on 2026-10-19 (10:39-10:41) in a session started after accio 0.2.0 was installed.

- **/1 pass.** The main chat started `accio:howler` in the background for the real 0.2.0 push (`877c699`, prev
  `89739c0`, CI run `39223845735` still running). Its report reached the chat on its own about 80 s later and matched
  `gh run view`: checks, accio-tests (ubuntu) and accio-tests (macos) PASSED, accio-evals SKIPPED. No prompt appeared.
  Caveats: it was started from the main chat, not from inside owl, and the session ran in auto mode, so whether owl's
  `allowed-tools` without `Agent` would prompt could not be seen. S-003/4 adds `Agent` to owl's `allowed-tools`
  anyway, so a prompt is avoided either way.
- **/2 pass.** Asked by message to run `ls`, howler was refused by curfew: "`ls` is not on the accio:howler exact
  list ... ask for it at owl". So curfew sees `agent_type: accio:howler` and applies howler's list.
- **/3 pass (platform).** A Bash call that outlives its `timeout` is moved to the background, not killed: "Command did
  not complete within its 3s timeout and was moved to the background (ID: ...). You will be notified when it
  completes." A Haiku subagent told to wait stopped with the work still running, was woken by the completion notice,
  and went on to read the output. Shown with a 25 s job and a 3 s timeout, since howler's commands cannot make a long
  job on demand; the real 0.2.0 CI took about 5 min, below howler's 600000 ms timeout. For S-003: howler's step 2
  says "If the watch times out, call it again"; a watch moved to the background has not timed out, so the prompt
  should say: when the watch is moved to the background, wait for its end notice, then go to step 3. Calling it again
  instead would only start a second watch.
- **/4 pass.** `gh run view 39170577637 --json jobs`: each job has `completedAt, conclusion, databaseId, name,
  startedAt, status, steps, url`; each step has `completedAt, conclusion, name, number, startedAt, status`. The failed
  job is `accio-tests (ubuntu-latest)` (databaseId `117802578910`), step `Python tests`. Everything the howler prompt
  needs (job `databaseId` for `--job`, job and step `name` and `conclusion`) sits inside `jobs`, which is in S-001's
  field set. Nothing is missing.
- **/5.** /1 passed, so there is no Blocked question; S-003 may start.
