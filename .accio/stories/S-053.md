## Context
After this ships: a build stops for the user only for a real decision, and every finding, block and break leaves a reason. We'd know because over the next two iterations no story blocks with "Should it be fixed and built again?" or on a one-off accio hiccup; each `.accio/iterations/<N>.md` has one line per finding and block saying how it ended; every boggart break that reached a fix round came with a repro that failed twice on head; owl reports a cost for every build; and the guard and allow-list tests pass.

Why this story: CI has been red on `accio-tests (macos-latest)` since 0.7.0 (runs 39425764883 and 39444021146; Linux passes). In both runs every test that starts a preview server fails with `accio-preview: http://127.0.0.1:<port>/marker.txt did not answer within 20s`: S-045_1 start, S-045_2 (both), S-045_3 stop-kills, S-049_3, S-049_5, and in 0.7.1 also S-051_1 and every round of S-051_3. Tests that start no server pass. The same tests pass on the user's Mac. So the cause is not the stop race S-051 fixed. The test server is `python3 -m http.server <port> --bind 127.0.0.1`, and `_answers` in `preview.py` checks it with plain `urllib.request.urlopen`.

Likely cause (unproven): on macOS, `urllib` takes proxy settings from the system (`_scproxy`) as well as the environment, so the check may go through a proxy and never reach 127.0.0.1. A preview check should never use a proxy anyway. The fix: `_answers` (and the tests' own `urlopen` calls) use an opener with `urllib.request.ProxyHandler({})`. If the cause is something else, the next CI run must say what: when `start` fails to get an answer, its error includes the last lines of the preview command's output, and a failing test prints that error.

Checked at planning (iteration 15): today a failed `start` calls `stop`, which deletes the story's preview log, so CI never shows the server's output; S-053/3 must read the log's last lines before that cleanup. The fix can only be seen on CI after a push, so S-053/4 is checked at release, not in the build.

The S-051_3 twenty-round test took most of the macOS job's 12 minutes, since each round waited 20s and failed. Once starts work, it should be quick.
