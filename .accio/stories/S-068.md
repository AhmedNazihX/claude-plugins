## Context
After this ships: a project whose UI is a native app (no web preview) still gets a visible-DoD walk from mad-eye on every story that touches its UI. We'd know because, on a project with a `ui_evidence` command, a story that touches `ui_globs` gets `mad-eye-findings.md` with one checked line per visible DoD line, citing a screenshot or element dump from the evidence folder, and a missing control shows up as a finding.

Why this story: found building Jaza (a SwiftUI macOS app) on 2026-10-23. mad-eye only has Playwright browser tools and runs only when `.accio/config.json` has a web `preview` with `test_data: true`, so on Jaza it never ran. Screens that merged as done but that nothing in the window opened, and panes with no live terminal, went unnoticed until a person looked. The author chose option A of three (2026-10-23): mad-eye reads evidence that UI tests produce, rather than driving the screen itself (option B: computer-use tools, rejected because it would take over the author's mouse and keyboard during unattended builds and break mad-eye's read-only design) or nothing (option C).

Design (to settle at prophecy; plan this after Jaza's S-030 shows its XCUITest smoke tests run): a new optional config entry `ui_evidence: {command, folder}`. prefect runs `command` in the story's worktree (for Jaza, an `xcodebuild test -only-testing:JazaUITests -resultBundlePath …` plus an export of attachments) and checks that `folder` then holds PNG screenshots and text element dumps (an XCUIElement hierarchy per screen). mad-eye gets a mode with Read only (no browser tools): it reads the review package and the evidence folder, checks each visible DoD line against the element dumps, cites the screenshot per line, and replies with the same findings JSON. Open questions: UI tests take over the screen and need Accessibility permission granted once by a person, so `ui_evidence` must say when it may run (every build, or only on a runner such as CI) and the workflow must skip with a note, not block, when it can't; how evidence older than the story's head is refused; whether `ui_evidence` and a web `preview` can both be set.
**Update 2026-10-24 (author's choice: extend mad-eye, no new reviewer).** Building Jaza that night showed three things this design must take in. 1) Element dumps can't catch the worst UI bugs: a pane that stayed blank (Jaza S-036, S-050) and a pane garbled after the window was minimized and restored (SwiftTerm paused painting while hidden) have the same element tree as a working pane. Only a real-window screenshot shows them. So mad-eye judges each visible DoD line from the **screenshots** (it reads PNGs with Read), in every theme the project names; dumps are optional extra evidence. 2) The evidence needn't come from XCUITest. Jaza will get a Debug-only walk mode that runs steps inside the app, with no Accessibility permission and no takeover of the mouse or keyboard, and captures its own real window per step (`screencapture -l <window id>` works with no permission prompt). So `ui_evidence.command` is any project command, and it takes a steps file: `{command, folder, steps_arg}`, e.g. `Jaza --ui-walk {steps} --out {folder}`. 3) The builder must not choose its own evidence. So mad-eye works in two passes: first it reads the review package and replies with a steps file for the visible DoD lines (from a vocabulary the project documents, e.g. `docs/ui-walk.md`; for anything with a terminal always including resize, minimize/restore and tab switching), the workflow runs the command with it, then mad-eye judges the screenshots and replies with the findings JSON. This removes the dependency on Jaza's S-030 and the "needs Accessibility once" question; XCUITest can still produce evidence later through the same entry. The open question that remains: evidence that opens windows on the author's screen during an unattended build, so `ui_evidence` says whether it may run while the author works (Jaza's walk opens its own window on its own `JAZA_ROOT` and never touches the author's running copy).
**Settled at prophecy (2026-10-24, defaults taken for the author, who may override).** 1) *May it run while the author works?* `ui_evidence` has a required `takes_over_screen` (true/false). `false` is the project's word that its command never moves the mouse, types, or takes keyboard focus from the author's apps, so it runs on every build (Jaza sets `false`; its walk should open its window without activating it). `true` (for example XCUITest) means it can't run in an unattended build: mad-eye is skipped with a note saying so. 2) *Config shape:* `ui_evidence: {command, steps_doc, takes_over_screen, themes?, timeout?}`. `command` must hold `{steps}` and `{folder}`; accio fills both. `steps_doc` is the repo file that documents the steps vocabulary (Jaza: `docs/ui-walk.md`). `themes` is an optional list of names (e.g. `["light", "dark"]`); without it only the app's default look is checked. `timeout` is seconds, default 600. 3) *Who writes what:* mad-eye has no write tool, so in pass 1 it replies `{"steps": "<file text>"}` and accio writes that text unchanged to `.accio/run/<ID>/ui-steps.txt`. accio picks the folder itself: `.accio/run/<ID>/ui-evidence/` in main (where mad-eye can Read it), emptied before each run, so nothing the builder left there counts. 4) *Old evidence:* after the command, accio writes the story's head commit to `.accio/run/<ID>/ui-evidence.head`. mad-eye is given the folder only when that stamp matches the story's current head; otherwise it is skipped with a note naming both commits. 5) *Both set:* config refuses `preview` and `ui_evidence` together ("set one"). 6) *Where the code goes:* the run-and-check work (empty the folder, fill the placeholders, run in the story's worktree with the time limit, count PNGs, write the stamp) lives in Python as `accio-preview <ID> evidence` (in `preview.py`), with unit tests, so `brew.js` (753 lines) only adds the stage calls and stays near its size. 7) mad-eye stays one agent (the author's choice): the evidence mode is a different prompt in which it uses only Read.
## Reuse
mad-eye's findings JSON and `mad-eye-findings.md` writing in `accio/workflows/brew.js` (`madEyeStage`, `previewStep`); `preview.start/stop` in `accio/bin/accio_lib/preview.py` for the run-and-clean-up pattern; config loading in `accio/bin/accio_lib/config.py`.
## Definition of Done
- [ ] S-068/1 WHEN config has `ui_evidence` and a story's diff touches `ui_globs` THE SYSTEM SHALL ask mad-eye for a steps file for the visible DoD lines, run the command with it in the story's worktree, and give mad-eye the evidence folder instead of a preview
- [ ] S-068/2 WHEN the evidence command fails, runs past its `timeout`, or leaves the folder with no PNG screenshots THE SYSTEM SHALL skip mad-eye with a note naming why, not block the story
- [ ] S-068/3 WHEN mad-eye judges evidence THE SYSTEM SHALL check each visible DoD line by looking at its screenshots (and element dumps when present), in every theme the project names, and cite one screenshot per line, using only Read
- [ ] S-068/4 WHEN a visible DoD line's screen is missing, blank, garbled or wrong in its screenshots THE SYSTEM SHALL report a finding that goes to a fix round, as for a web preview
- [ ] S-068/5 WHEN the evidence folder's `ui-evidence.head` stamp is missing or names a different commit than the story's current head THE SYSTEM SHALL refuse it: mad-eye is skipped with a note naming both commits
- [ ] S-068/7 WHEN `ui_evidence.takes_over_screen` is true THE SYSTEM SHALL not run the command and SHALL skip mad-eye with a note that the command takes over the screen and can't run in an unattended build
- [ ] S-068/8 WHEN config sets both `preview` and `ui_evidence`, or `ui_evidence` lacks `command` (with `{steps}` and `{folder}`), `steps_doc` or `takes_over_screen` THE SYSTEM SHALL refuse the config with a message naming the problem
- [ ] S-068/6 (no test) checks pass: `python3 tests/run_tests.py`
