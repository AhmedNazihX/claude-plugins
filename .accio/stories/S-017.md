## Context
After this ships: a build's check step takes about 1 minute instead of about 5, and CI's macOS job about 1 minute
instead of about 4, with every test still run. We'd know because the next build's check step (the prefect agent's
`accio-check` call) finishes in under 2 minutes.

Why: in iteration 4 the check step took 302 s of a 562 s build. Nearly all of it is
`python3 -m unittest discover -s tests` (628 tests, 294 s on the user's Mac; CI macOS 247 s, ubuntu 115 s). The
suite is CPU-bound in one process (user 147 s + sys 108 s): most tests start `python3` hook scripts or `git`. Run
by hand on 2026-10-19 with each `tests/test_*.py` file in its own process, 8 at a time
(`xargs -P 8 ... python3 -m unittest <module>` from `accio/tests`), the same suite passed in 51 s. The user chose
this over running only the tests near the changed files, or rewriting the slow tests.

The runner is `accio/tests/run_tests.py`, plain Python with the standard library only. Its name does not start with
`test`, so `unittest discover` never loads it as a test. It works from any folder (it finds its own folder), runs
every `test_*.py` in that folder as `python3 -m unittest <module>` with that folder as the working directory (the same
import path `discover -s tests` gives), at most `--jobs N` at once (default: the number of CPUs, at most 8). It prints
one line per file (passed or FAILED, and seconds), then the full output of each failed file, then a total line. It
exits 0 only when every file passed; it exits non-zero when any file failed, when a file could not be started, or
when it found no test file (an empty run must never pass, see S-010). `--verbose` passes `-v` to each file.

After the merge, the main chat (not the builder) changes the `python3 -m unittest discover -s accio/tests` entry in
`.accio/config.json` to `python3 accio/tests/run_tests.py`, and the test line in `CLAUDE.md`; those two files are
outside this story's files.
